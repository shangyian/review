How Caches Work

A cache keeps a copy of data somewhere faster to reach than where it normally lives. This page follows one shared cache from its first read to the day it fails. Each screen starts with what goes wrong, adds one idea, and says what it costs.

1A cache is a copy kept closer to the reader

The problem

The same data is read again and again, and every read goes to the database. Each one costs a network hop and a read from memory or SSD, and the database serves all of them.

The fix

Keep a copy where it is faster to reach. There are two common places:

  • Inside each app process. There is no hop, but every server holds its own copy, so two servers can give different answers and each one has to fill its own.
  • In a shared cache such as Redis or Memcached. It is one hop of about 0.5 ms, but there is one copy that every server sees, and it survives an app restart.

The price

Either way it is a copy. The database stays the source of truth, which is why a cache can usually drop an entry safely: it can be read again later. source

The rest of this page uses a shared cache.

2The app asks the cache first, and the hit rate decides the gain

The problem

Someone has to decide when the cache gets filled.

The fix

The common answer is to fill it on demand. The app asks the cache. On a hit it uses the answer. On a miss it reads the database and writes the result into the cache for next time. Facebook calls this a demand-filled look-aside cache. source

What a request touches

  • Hit: app to cache and back, one hop.
  • Miss: app to cache, then to the database, then the result goes into the cache. That is more work than having no cache.

Take an example with a cache read of 0.5 ms and a database read of 5 ms. At 90 hits in 100, the average read is about 1.0 ms and 10 reads reach the database. At 99 hits in 100, the average is about 0.55 ms and 1 read does. Going from 90 to 99 percent cuts database reads tenfold, though the average time only about halves. The 5 ms is an example, not a measurement.

The price

You have to watch the hit rate. Redis counts keyspace_hits and keyspace_misses, and hits divided by their sum is the share of reads the cache answered. source

3The data changes, and the cache must find out

The problem

The cache holds a copy, and someone changes the original.

The fix

There are four common ways to keep the copy honest:

  • Expire it. Give each entry a time limit and let it disappear. It is simple, but the copy can be old until the limit. In Redis, overwriting a key with SET removes its time limit, so it has to be set again. source
  • Delete on write. Write the database, then delete the cache entry, and the next read refills it. Facebook deletes instead of updating because a delete is safe to repeat. source
  • Write both (write-through). The app updates the database and the cache together, so they can disagree if one write fails or the two interleave.
  • Write the cache first (write-behind). It is fast, but the change is lost if the cache dies before the database has it.

The price

The cache and the database are separate systems, so nothing updates both in one step. Delete on write has a race, shown in the diagram: a reader fetches the old value, a writer then updates the database and deletes the key, and the reader puts the old value back. It stays there until it expires.

Facebook closes this gap with leases. On a miss, the cache gives the reader a token, and the reader can only fill the cache if no delete has arrived since. source A short expiry time is a common backstop for races you did not foresee.

4Memory is limited, so something gets dropped

The problem

The cache is in RAM, and RAM is smaller than the data. When it is full, a new entry needs room.

The fix

Pick an eviction policy, which decides what to drop. Redis offers, among others:

  • allkeys-lru: drop the least recently used. The docs call it a good default when a subset of keys is read far more than the rest. source
  • allkeys-lfu: drop the least frequently used.
  • allkeys-random: drop at random, for when all keys are read about equally.
  • noeviction: drop nothing, and return an error to writes that need space.

Redis approximates LRU by sampling a few keys and dropping the oldest of them, not by tracking an exact order. Memcached is a least-recently-used cache by default, and its entries can also expire after a set time. source

The price

A dropped entry that is needed again is a miss. A bigger cache raises the hit rate, with diminishing returns once the hot data fits. Redis suggests comparing evicted_keys with expired_keys to see whether entries are going because of the policy or because the time limits are too short. source

5A popular entry expires, and everyone asks at once

The problem

When a very popular key disappears from the cache, whether by expiry, eviction or a delete, every request for it misses together. All of them go to the database for the same value, and the database sees a spike. This is often called a stampede, or a thundering herd.

The fix

Let one request do the work.

  • One refills, the rest wait. The Facebook memcache hands out a lease token on a miss, at most once per key every 10 seconds. A request that arrives meanwhile is told to wait a short time, and by the retry the value is usually there. For the keys they measured over a week, the peak database query rate fell from 17,000 per second to 1,300. source
  • Serve the old value briefly. The same paper keeps a deleted value around for a short time so that readers who can tolerate stale data do not have to wait. source
  • Spread out expiry times with a little random jitter, and refresh before expiry, so popular keys do not all vanish together. These are common techniques, described here from general knowledge and not from the sources below.

The price

Waiting requests are slower, serving old values means some users see stale data, and all of it is extra code to write and test.

6The cache is empty or down

The problem

After a restart the cache is empty, and during an outage it does not answer. Either way, reads that it normally absorbs fall on the database. Facebook describes how losing memcache can overload backend services and cause further failures in a cascade. source

The fix

Decide what happens before it happens:

  • Fall back to the database, and know whether it can take the full read load.
  • Fail fast, returning an error to protect the database.
  • A spare pool. Facebook dedicates about 1% of its memcached servers to take over for failed ones. A client that gets no answer asks the spare, and entries there expire quickly. They report this cut client-visible failures by 99%, and turned 10% to 25% of failures into hits each day. source

Filling a new cache before it takes traffic is also common, and is from general knowledge here.

The price

A spare pool costs machines, and what it serves can be slightly stale.

7One cache node cannot hold everything

The problem

One cache machine has limited memory and network capacity, and it is another single point of failure.

The fix

Run several nodes and let the key decide which node holds it. In Memcached the client does this: it hashes the key to pick a server, and the servers do not know about each other, with no synchronization or replication between them. source

The price

If a node dies, its share of keys is cold, and those reads go to the database. Rehashing the keys across the remaining nodes sounds natural, but Facebook warns that it can cascade: a single key can account for 20% of the requests to one server, and the node that inherits it may be overloaded. source

A hot key also lives on one node, so adding nodes does not spread the reads of that key.

When not to cache

  • Data that must be exact, such as an account balance. A stale copy is a wrong answer.
  • Data that is rarely read twice, such as per-user pages. The hit rate stays low, and every miss costs extra.
  • Very large values. They use memory fast and push out many small entries.

Measure the hit rate before adding one, and remember the cache is a copy: the database is where the truth lives.

Write-through, write-behind, jitter, refresh before expiry, warming a new cache and the 5 ms database read are from general knowledge or examples, not from these sources. The 0.5 ms hop is the rounded figure from the Latency Ladder page.
