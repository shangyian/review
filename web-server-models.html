Web Server Models

A web server runs your code for many requests at once. Servers do this in very different ways, and the differences set how many requests they can take, how much memory they use, and what rules your code must follow. This page starts with the two choices every server makes, then goes through the options one at a time.

1Many requests arrive at once, and each spends most of its time waiting

The problem

A web server handles many clients at the same time. For each request, your handler does a few milliseconds of real work and then waits, usually for a database. A server that does one thing at a time would spend nearly all its time idle.

The shape

A listener accepts connections. For whichever program is listening, whether that is nginx or the app server on its own, the operating system finishes each TCP handshake and queues the finished connections until the program takes one. Workers take requests from there and run your handler, which talks to the database.

The question

How many requests can be in progress at once, and what does each waiting request cost? That sets the capacity. By Little's law, the number of requests in progress equals the arrival rate times the time each one takes. source

The rest of the page is about the different answers servers give.

2Every web server answers two questions

The two layers

  1. Layer 1: how many processes? One, or several started by a master process (pre-fork).
  2. Layer 2: how does one process run many requests? One at a time, with a pool of threads, with an event loop, or with lightweight threads.

Servers that look unrelated are usually different combinations of these two choices.

3One process uses one core, and one crash ends it all

The problem

A single process can use only so much of a machine. In CPython, only one thread runs Python code at a time (the GIL), so one process can't use several cores. A crash or an out-of-memory kill in that process also stops every request it was handling.

The fix: pre-fork

A master process opens the listening socket and then forks several worker processes. Each worker inherits the open socket and accepts connections from it, and the kernel hands each new connection to one waiting worker. The master doesn't handle requests. It restarts workers that die or hang.

What a request touches

The kernel's handshake and accept queue, then one worker, then your handler, then the database through that worker's own connection.

The price

  • Each worker has its own memory. Pages are shared right after the fork, but they are copied as a worker changes them, so the sharing shrinks over time.
  • An in-process cache is duplicated in every worker.
  • Every worker holds its own database connections, so connections multiply with the number of workers.
  • The benefit is isolation. A bad request or a leak affects one worker, and the master replaces it.

Pre-fork only answers layer 1. What a worker does inside is the next question.

4One request at a time is simple, until requests wait

How it works

This is gunicorn's default sync worker. It handles one request per worker at a time and closes the connection after each response. Its docs say it needs a buffering proxy such as nginx in production. source

The docs suggest starting with (2 × cores) + 1 workers, and warn that workers are not clients: they say 4 to 12 workers typically handle heavy traffic, and too many waste resources and can reduce throughput.

The problem it runs into

Say there are 4 workers and each request takes 100 ms, of which 80 ms is waiting on the database. Capacity is about 4 ÷ 0.1 = 40 requests per second, and each worker is idle most of the time.

A slow client is worse. If one takes 2 seconds to send its request, that worker is stuck for 2 seconds, and four such clients stall the whole server. nginx collects the full request first and hands it over in one quick step.

The price

Simple and easy to reason about, but capacity is only the number of workers, and every wait on a slow dependency uses one up.

5Processes are heavy, and a waiting worker is idle

The fix: a thread pool

Run a pool of threads inside each process. Threads share the process's memory, so each one costs far less than another process. While one thread waits on the database, others run. gunicorn's gthread worker works this way, with a thread pool inside each worker process, and it supports keep-alive. source Java servlet containers such as Tomcat use a thread pool inside one process.

What a request touches

The accept queue, then one free thread, then your handler, then a connection borrowed from a shared pool.

The price

  • Shared memory means shared state, so code must be thread-safe.
  • In CPython, the GIL means threads help with waiting but not with running Python code in parallel. JVM threads run in parallel across cores.
  • Threads share a pool of database connections, so there can be hundreds of threads and only a few connections. Threads then wait for a connection, which is a second waiting line.
  • A thread that is waiting still holds a thread. Thousands of them get expensive.

6Threads still sit idle while they wait

The fix: an event loop

One thread runs many requests. When a handler has to wait, it pauses and saves where it stopped, and the loop runs another. The operating system does the waiting. Node's docs describe this as non-blocking I/O with a single JavaScript thread, by offloading operations to the system kernel. source

  1. Request A arrives. The loop runs the handler until it awaits the database, sends the query, and pauses A.
  2. B and C arrive and do the same. Three queries are in flight and the thread is idle.
  3. The database answers A. The loop resumes A where it paused and finishes it. Then B and C.

A paused request costs only its saved state in memory. nginx, which is event-driven with about one worker per core, uses this to hold very large numbers of connections cheaply. source

The price

  • Blocking freezes the loop. Python's docs say that if a function does a CPU-intensive calculation for 1 second, all concurrent tasks and I/O are delayed by 1 second. source Blocking work goes to an executor, which runs it in another thread or process.
  • One loop uses one core. To use more, run several loops, one per process (nginx, or gunicorn with uvicorn workers) or one per thread.
  • The handler must be written for it. In Python that means async def with an ASGI server. gunicorn's ASGI worker runs an asyncio loop in each worker. source

7Blocking-style code with event-loop efficiency

The fix: lightweight threads

Write ordinary code that looks like it blocks, and let a runtime make it cheap. A runtime scheduler runs very many lightweight threads on a few OS threads, and parks one whenever it waits on the network.

  • Go: the standard HTTP server accepts connections and creates a new service goroutine for each. source
  • Java virtual threads: a virtual thread is not tied to a particular OS thread. When one blocks on I/O, the runtime suspends it and frees its OS thread. They are for scale, not speed. source
  • gevent: gunicorn's greenlet-based worker, which can handle thousands of concurrent connections. source

The price

  • Nothing in the model limits how many run at once. Under overload that shows up as memory use and database waits, unless you add limits yourself. The database pool is still a hard limit.
  • There are exceptions. In Java, a virtual thread inside a synchronized block, or in a native call, can't unmount and holds its OS thread.
  • gevent needs libraries patched to cooperate, and it doesn't work with code that depends on blocking behavior.

8async/await looks the same everywhere, but it isn't

The confusion

async and await are syntax that says "this code can pause here". What actually runs the paused code differs by language.

  • Python asyncio: an event loop runs in a thread and runs all tasks in that thread, one at a time. When a task awaits, it is suspended and the loop runs the next one. source
  • Rust's Tokio: a multi-threaded scheduler with work stealing and, by default, one worker thread per core. source
  • .NET: as I understand it, the rest of a method after an await typically resumes on a free thread-pool thread. This one I haven't checked against the docs.
  • Go: no await at all. Goroutines on a scheduler, as in the last screen.

The question to ask of any server

What carries a request while it waits? A whole process (pre-fork, one at a time), a thread (thread pool), or a paused task or lightweight thread (event loop and the rest). The first costs the most memory per waiting request, and the last costs the least.

9Putting it together

A typical Python setup

nginx in front, gunicorn behind it. nginx handles the secure handshake and slow clients, and hands whole requests to gunicorn's workers over a fast local connection. Inside each worker you pick the model that fits your code. gunicorn's docs suggest sync for a simple app behind nginx, gthread when you need keep-alive or moderate concurrency, and gevent or an ASGI worker for WebSockets, streaming or async frameworks. source

There are two separate connections. The client connects to nginx. The operating system completes that TCP handshake, and then nginx does the TLS handshake. nginx then opens a second connection to gunicorn. That one is often a Unix domain socket, a link between two programs on the same machine addressed by a file path, which needs no TCP handshake at all. It can also be a local TCP port, where the handshake is fast. gunicorn only ever talks to nginx.

What stays true in every model

  • Capacity is concurrency divided by time per request, so a slow dependency lowers capacity.
  • Database connections add up: servers × workers × pool size. Postgres, for example, defaults to about 100 connections, so a few busy servers can exceed it. source
  • The model decides what a waiting request costs and which rules your code must follow, such as thread safety or never blocking.
