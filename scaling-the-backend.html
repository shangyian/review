Scaling the Backend

A request has just reached the backend. This page grows a backend one problem at a time. Each screen starts with what hurts, adds one fix, and says what the fix costs. Where there are several copies of the data, the cost is usually consistency, and PACELC is the name for how that cost is paid.

PACELC: if there is a network Partition, a system must choose Availability or Consistency. Else, in normal operation, it must choose Latency or Consistency. source

1Everything on one machine

The problem

None yet. This is a new site with a few requests a second and a small amount of data. It is the baseline the rest of the page builds on.

What it is

One machine runs nginx, gunicorn with several worker processes that run your code, and the database.

What a request touches

CPU, then RAM (the operating system's cache and the database's own cache), then SSD on a miss. No network hops.

The price

It is simple and fast, and consistency is free because there is only one copy to disagree with. But it is one point of failure. While the machine is down, so is the site. The data survives a crash because it is on SSD, but it is lost if the disk is, unless it was backed up.

Many sites never need more. When it does get slow, the first moves are cheap ones: tune the slow queries, add workers, or move to a bigger machine. Add a new piece only when a measured problem calls for it. The screens below are in a teaching order, not a fixed history. Real systems often add a cache or a replica before a second app server.

2The app and the database compete for one machine

The problem

A heavy query slows page rendering, and a busy app slows the database, because both use the same CPU and memory. You also cannot size them separately.

The fix

Move the database to its own machine.

What a request touches

CPU, then a network hop of about 0.5 ms for each query, then the database's RAM or SSD. A page that runs ten queries one after another pays about 5 ms in hops alone.

The price

A hop on every query, and code that queries in a loop gets expensive. There is still one copy of the data, so there are no stale reads. If the network between the two breaks, the app cannot answer. It fails rather than guess.

3One machine cannot be big enough, and cannot be allowed to fail

The problem

You have already tuned queries, added workers and bought a bigger machine. Three things still push you to more than one app server:

  • Size has a ceiling. A machine has a fixed number of cores and amount of memory, and the biggest ones cost far more per unit of capacity.
  • Availability. If the one app server dies, the site is down.
  • Deploys and restarts. Replacing the code on a single server drops requests unless a second server takes them meanwhile.

To see how much one server can take, look at how many requests it can run at once. Each client connection is state the operating system keeps in memory, reached by the server program through a file descriptor. A typical Python setup puts nginx in front of gunicorn:

  • nginx is a reverse proxy. It handles the secure handshake, serves static files, and holds the slow client connections. It is event-driven, with about one worker process per core, so each connection costs a file descriptor and a little memory, not a thread. source Its own limit is set by worker_connections (default 512 per worker) and the open-file limit. source
  • gunicorn runs your Python code in a few worker processes. The default sync worker handles one request at a time and has no keep-alive, and the docs say it needs a buffering proxy such as nginx in production. They suggest starting at (2 × cores) + 1 workers. source

So application concurrency is the number of workers, not the number of open sockets. With Little's law, concurrent requests = arrival rate × time per request. source Rearranged, 8 workers at 100 ms per request handle about 80 requests per second. If a slow database makes each request take 1 s, the same workers handle about 8. A latency problem turns into a capacity problem.

How web servers run many requests at once →

The fix

Run several app servers behind a load balancer. Clients need one address, and something has to spread the requests and skip a server that is down.

The app servers must be stateless, so any of them can handle any request. A session kept in one server's memory would vanish when the next request lands on another, so that state moves to a shared place such as the database or a cache.

What a request touches

One more hop of about 0.5 ms at the front, then an app server, then the database.

The price

The database is now shared by every worker, and connections to it are limited. Postgres, for example, defaults to about 100 connections source and runs one process per connection. source Twenty servers × 8 workers × 2 connections each is 320, well above 100, so a connection pooler usually sits in front. The load balancer must also not become the new single point of failure, so it needs a backup.

4Reads overwhelm the database

The problem

Reads pile up on one database. Some are the same popular rows and pages, read thousands of times a second. Others are all different. Each read goes to the database, which reads from SSD under load, until the database is the bottleneck. There is also only one copy of the data.

Fix 1: a cache

Put a cache in front of the database, either inside each app process or shared, such as Redis or Memcached. A hit never reaches the database.

  • Hit: app to cache, RAM over one hop of about 0.5 ms.
  • Miss: app to cache, then to the database and its SSD, then the result is written into the cache. A miss costs more than having no cache.

Price: a cached value can be out of date, and deciding when to remove it is hard. How caches work and fail →

Fix 2: read replicas

Add copies of the database that follow the primary. Reads go to the replicas. Writes go to the primary, which ships its log of changes to them.

  • Read: app to a replica, one hop plus RAM or SSD.
  • Write: app to the primary, one hop plus an SSD write to its log, then copied to the replicas.

Price: with asynchronous copying, replicas lag. A user can save something and then read the old version, and after a failover the newest writes can be lost. With synchronous copying every write waits for a replica to confirm, which is slower. What goes wrong with copies, and the fixes →

Normally: asynchronous replication is latency over consistency, and synchronous is the reverse. During a partition: promote a replica (available, but writes may be lost or forked) or stop accepting writes (consistent).

Which to choose

  • A cache fits when the same few rows or pages are read again and again, some staleness is fine, and you want sub-millisecond reads. A good hit rate removes most of the load. It does not help with a long tail of different queries, and you write the invalidation logic.
  • Replicas fit when reads are varied, such as ad hoc queries and reports, or when you cannot accept cache invalidation. Any query can run on a replica, and capacity grows with each copy. A replica can also be promoted if the primary dies, which a cache cannot.

Large systems usually use both: the cache takes the hot reads and the replicas take the rest.

5Slow jobs hold requests open

The problem

Some work takes seconds or minutes, such as processing a video, building a report, sending email or running a model. A request that waits for it ties up a worker for that whole time, which from screen 3 means less capacity for everyone, and the user may hit a timeout.

The fix

Accept the request, write a job to a durable queue, and reply at once with "accepted" and a job ID. Separate workers pick the job up later. The user checks back or is notified.

Getting the result back

The browser still has to learn when the job finishes. There are four common ways, and the page's JavaScript starts all of them:

  • Short polling: a timer asks "done yet?" every few seconds. Each ask is an ordinary request that the server answers at once. It is simple, but most answers are empty and the result can arrive up to one interval late.
  • Long polling: the same kind of request, except the server holds it open until the job finishes or about 30 seconds pass. The browser then asks again. There are far fewer empty answers and the result arrives quickly, but a connection stays open for each waiting user. The wait must stay shorter than every timeout between the browser and the server.
  • Server-sent events: one HTTP request that the server never finishes, with updates streamed into it. It is one-way, and the browser reconnects by itself.
  • WebSocket: a request asks to upgrade, and the same connection then carries messages both ways. It is a different protocol and needs server support.

The last three hold a connection for each waiting user, so they need a server that can hold many clients while running few requests. How web servers run many requests at once →

Workers face the same choice when they fetch jobs from the queue. Amazon SQS, for example, answers a short-polling receive at once even if the queue is empty, while a long-polling receive waits up to 20 seconds for a message, which cuts empty responses and cost. source

What a request touches

A short path: app to queue (a network hop and a durable write, a few milliseconds), then the reply. The slow work runs off the request path.

The price

"Accepted" and "done" disagree for a while. A job can run twice after a failure, so the work has to be safe to repeat. You also need job status, retries, and a plan for jobs that keep failing. What happens when jobs arrive faster than they finish →

Normally: latency over consistency. The reply is instant, but the result is not ready yet. During a partition: the queue can keep accepting work (available) while processing falls behind.

6One database can't hold the data or the writes

The problem

Replicas do not help here. Every copy holds all the data, and one primary takes all the writes. Once the data outgrows what one machine handles comfortably, or the writes saturate it, you need a different split.

The fix

Shard the data: split it by key across several databases, each with its own copies, and route each request to the right one.

What a request touches

Work out the shard from the key, then one hop to that shard.

The price

A query or transaction that spans shards needs several hops and coordination. One shard can get hotter than the others, and moving data between shards is hard. If a shard is unreachable, its slice of the data is unavailable.

Normally: keeping a cross-shard change consistent costs latency, and skipping that costs consistency. During a partition: the unreachable slice is unavailable.

7Many teams are blocked on one codebase

The problem

One codebase and one release for everyone means teams collide, one bug can take down everything, and parts that need different amounts of capacity scale together.

The fix

Split the app into services. Each owns its own data and calls the others over the network.

What a request touches

One user request fans out into calls between services. Calls that depend on each other add up: five in a row is about 2.5 ms in hops alone, and the slowest call sets the pace.

The price

Latency accumulates, and any one slow service slows the whole request. This fix is as much about organizing teams as about capacity. It adds hops and does not remove load.

Normally: there is no single transaction across services. Either they agree eventually (a series of steps with an undo for each, so latency and availability win) or they use distributed transactions (consistent, slower). During a partition: a service that cannot reach another degrades or fails that part.

8Faraway users pay about 150 ms per round trip

The problem

A user on another continent pays the ocean rung on every round trip, about 150 ms from California to the Netherlands and back. A whole region failing also takes the site down.

The fix

Run a second region with its own copy of the stack, and send each user to the nearest one.

What a request touches

Reads stay local. Writes either cross regions to a home copy, which costs the ocean rung, or are applied locally and copied afterward.

The price

You choose between fast writes that regions can disagree about for a while, and consistent writes that wait on a cross-region round trip. Conflicting writes in two regions need a rule for who wins.

Normally: synchronous agreement across regions is consistent but pays about 150 ms per write. Asynchronous is fast and local, and consistency is the price. During a partition between regions: both sides keep serving (available, and they diverge and reconcile later) or one side stops (consistent). This is the full PACELC choice, and systems differ on where they land. source

9When the best fix is to skip the backend

The idea

Every fix above makes the backend handle more. The cheapest request is one it never sees. Answer from the CDN, serve pages that were built ahead of time, or run small functions only when a request arrives. Each has its own price, such as staleness at the CDN or a slow first request for a function that has not run recently.
