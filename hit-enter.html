Hit Enter

What happens between pressing Enter on a URL and seeing the page. Each step shows what it gives you, why it is there, and what it hands to the next step. In the diagram, the lines on the right skip ahead when a cache already has the answer.

1HSTS check microseconds

You get the scheme decided: https://, before any request leaves.

What happens

If you type http://example.com or just example.com, the browser checks whether that site has told it to be HTTPS-only (HSTS). If so, the browser upgrades the address itself.

Sites send a header, Strict-Transport-Security, and the browser remembers it for a set time. Browsers also ship a built-in list for large sites, so even a first visit is covered.

Why it is there

It skips the insecure first request and the redirect from HTTP to HTTPS, which saves a round trip. It also stops someone on the network from forcing you onto plain HTTP.

Feeds step 2: the full https URL is what gets looked up in the cache.

2HTTP cache microseconds to a few ms

You get either a fresh copy of the page and nothing more to do, or what the browser needs to ask the server whether it changed.

What happens

The browser keeps a store of earlier responses (HTML, CSS, JS, images, API replies). A memory layer sits in front of files on disk, keyed by URL and the site you were on.

  • Fresh: the server said "reuse this for N seconds" (Cache-Control: max-age) and N has not passed. The browser uses it with no network at all, skipping steps 3 to 9.
  • Stale: the browser keeps the ETag and later asks "has it changed?". An unchanged page comes back as 304 Not Modified with no body. That still costs a round trip, but not the download.
  • Miss: carry on to step 3.

Why it is there

The fastest request is the one never sent. A cache hit costs microseconds, against 20 ms or more for the network.

Sites usually cache hashed CSS, JS and images for a long time, but give the main HTML a short lifetime so it is revalidated.

Feeds step 3: on a miss or stale entry, the browser needs a server to talk to, so it needs an address.

3DNS 0 if cached, ~20 to 100+ ms cold

You get an IP address, usually that of a CDN server near you.

What happens

Names are not routable, so the browser has to turn example.com into an address. It checks its own cache, then the operating system's, then asks a resolver (often your ISP's or a public one). The resolver asks the authoritative servers if it does not already know.

For a site behind a CDN, the answer is the address of a nearby edge server. The CDN either answers differently depending on where you are, or uses one shared address routed to the closest location.

Why it is there

Every connection needs an address. Answers are cached for the time the record allows, so most lookups never leave your machine.

Feeds step 4: the browser connects to that IP address.

4TCP handshake 1 round trip, ~20 to 50 ms

You get a reliable, ordered stream to the edge server.

What happens

The edge is the CDN's server nearest you, not the site's own servers. Your machine opens a connection to it on port 443 with three small messages: SYN ("want to talk"), SYN-ACK ("ok, me too"), ACK ("confirmed"). The first real data can ride with the third message.

The internet's basic layer only delivers packets, and they can be lost, duplicated or arrive out of order. TCP numbers the bytes, resends what goes missing, puts them back in order and slows down when the network is congested.

Why it is there

TLS and HTTP both need a clean pipe to run on. TCP provides it. It does not check who is on the other end, and everything it carries can be read by anyone on the path.

Feeds step 5: TLS runs inside this stream, so it cannot start until the stream exists.

5TLS handshake 1 round trip, ~20 to 50 ms

You get proof you are talking to the real site, and a private channel nobody can read or change.

What happens

  • Identity. The server sends a certificate saying "this public key belongs to example.com", signed by a certificate authority your browser trusts. The browser checks the signature, the name and the expiry. The server then proves it holds the matching private key by signing part of the handshake.
  • Privacy. Both sides agree on shared secret keys. All later traffic is encrypted.
  • Tamper detection. Every message is authenticated, so changes in transit are noticed.

In TLS 1.3 this takes one round trip. The browser sends the encryption options it supports and its half of a key exchange. The server replies with its choice, its half, its certificate and a signature. Both sides can then compute the same keys.

Why it is there

Without it, anyone on the path could read the page, change it, or pretend to be the site.

HTTP/3. It runs over QUIC instead of TCP and merges steps 4 and 5 into one round trip, or none on a repeat connection. A first visit often still uses TCP, because I believe the browser learns about HTTP/3 from a header on the first connection. Browsers differ on this.

Feeds step 6: the HTTP request can now be sent, encrypted.

6Request to the CDN edge 1 round trip, ~20 to 50 ms

You get the page straight from the edge, if it already has a copy.

What happens

The browser sends a GET request with headers such as cookies and cache validators. The edge looks in its own cache, held in its memory and on its SSDs. If it has a fresh copy it answers at once, in about a millisecond.

Why it is there

This is what a CDN is for. Most requests are answered from nearby, and never cross to the origin.

Feeds step 9 on a hit, skipping steps 7 and 8. Feeds step 7 on a miss.

7Edge to origin 1 round trip, ~50 to 150 ms

You get the page from the origin, when the edge did not have it.

What happens

The edge forwards the request to the site's own servers. CDNs usually keep connections to the origin open, so this costs one round trip and not a fresh TCP and TLS setup. Details differ between CDNs.

Why it is there

Someone has to hold the real data. This is often the longest single trip of the whole story, because the origin may be in another region or on another continent.

Feeds step 8: the request arrives at the origin's front door.

8Origin builds the page ~2 to 20 ms

You get the HTML, plus headers saying how long it may be cached.

What happens

A load balancer passes the request to an app server. The app checks a cache such as Redis (data in RAM, reached over the network), and on a miss reads the database, which reads from SSD. Hops inside the datacenter cost about half a millisecond each.

Lookups that do not depend on each other can run in parallel. Queries that run one after another add up.

Why it is there

This is where your data lives and your logic runs. It is also the one step where RAM and SSD matter, and they cost far less than the internet trips on either side of it.

Feeds step 9: the finished response heads back.

9Response comes back 1 round trip plus transfer

You get the HTML in the browser, and copies stored along the way for next time.

What happens

The edge stores a copy according to the cache headers, so the next visitor gets a hit at step 6. The browser stores one too, for step 2 on your next visit.

A page of about 100 KB is limited more by bandwidth than by latency. The browser starts parsing as the first bytes arrive, so this step and the next overlap.

Why it is there

The cache headers decide how much work future visits skip. A few seconds of reuse and a year of reuse lead to very different load times.

Feeds step 10: the HTML is what the browser reads to find everything else.

10Parse the HTML 1 round trip per dependency level

You get a list of everything else the page needs: CSS, JavaScript, fonts, images and other domains.

What happens

  • Requests go out in parallel over the open connection (HTTP/2). Each one repeats steps 2 and 6: a cache check, then the edge.
  • Other domains, such as analytics or fonts, need their own DNS, TCP and TLS first. They run alongside the rest.
  • Chains cannot run in parallel. HTML to CSS to a font, or HTML to JS to an API call, costs a round trip per level.
  • CSS blocks the first paint. JavaScript can block parsing unless it is marked async or defer.

Why it is there

One page is many requests. This fan-out is where most of the page load time goes, which is why bundling, preloading and long cache lifetimes matter.

Feeds step 11: once the blocking CSS and scripts are in, the browser can draw.

11Render ~10 to 50 ms

You get pixels on the screen.

What happens

The browser builds the layout from the HTML and CSS, then paints it, using the CPU and GPU. JavaScript can run, change the page and call APIs, which sends the browser back through steps 2 and 6 with new requests.

Why it is there

This is the point of everything above. A cache hit at step 2 jumps straight here, which is why a repeat visit can feel instant.

Reading the numbers: every time is a rough, typical figure for a first visit. Round trips over the public internet are 20 ms or more each, so the count of sequential round trips matters more than anything that happens inside the origin.
