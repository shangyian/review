Backpressure

When work arrives faster than it can finish, something has to give. This page runs one small server through a traffic spike and adds one fix per screen. The simulation is live, so the controls change the curves.

1Work arrives faster than it finishes

What you see

A server has 8 workers, and each finishes a request in 100 ms, so the server completes 80 requests per second. Normally 60 arrive each second. From second 20 to second 60 there is a spike. A request that cannot start at once waits in a queue.

What it tells you

Every second that arrivals exceed 80, the queue grows by the difference. At 120 per second it grows by 40 each second, so by second 60 it holds about 1,700 requests and a new arrival would wait about 21 seconds. The arithmetic is the same Little's law used on the backend page.

When the spike ends, the queue does not vanish. The server has only 20 per second to spare (80 finished, 60 arriving), so draining takes around 80 more seconds. Nothing is wrong with any single request, because each takes 100 ms once it reaches a worker. The waiting is the whole problem, and it lasts long after the cause is gone.

2An unbounded queue turns overload into delay, then waste

What you see

The same spike, now with callers who give up after 5 seconds. A caller abandons a request that waited longer, but nothing tells the server, so the abandoned request stays in the queue.

What it tells you

Wait time is the queue length divided by 80, so once more than 400 requests are waiting, a new arrival waits longer than the callers' patience. From then on the server works through requests nobody is waiting for. In the second chart the blue line (finished in time) falls toward zero and the orange line (wasted) takes over. Within seconds of the queue passing that mark, almost none of the 80 requests per second finished are useful. It stays that way well after the spike ends, because the queue is still full of abandoned requests.

The server is as busy as ever and is producing almost nothing useful. AWS describes the same thing: when a request times out, all the progress made on it is wasted, and it calls the share of work that finishes in time goodput. source Memory also grows with the queue. Google's SRE book says that without protection, work piles up and tasks eventually run out of memory and crash. source

3Bound the queue and say no early

What you see

Two limits sit in front of the queue: a cap on how many requests may wait, and an optional cap on how many are admitted each second. A request over either limit is rejected at once, with an HTTP 503 or 429, instead of being queued.

What it tells you

A bound turns unlimited delay into a known worst case. With 100 waiting and 80 finishing per second, nobody waits more than about 1.25 seconds, well inside the 5-second patience. Useful work stays near the server's capacity through the spike, and recovery is immediate when it ends.

An admission rate limit does the same job earlier and keeps the queue nearly empty. Its bigger use is fairness: a per-caller limit gives one heavy caller errors while the others carry on. Google's SRE book sets quotas per customer this way, and RFC 6585 defines status 429 for "too many requests". source source The simulation has one class of caller, so it cannot show the fairness part.

The price

Rejected callers get errors and must cope. Rejecting is cheap but not free: the SRE book notes that a backend can spend most of its CPU on rejections, and this simulation charges a tenth of a request for each one, an assumption of mine.

You also have to choose whom to drop. AWS suggests bounding the queue, discarding requests that have waited too long, and considering newest-first service where the protocol allows it. source Google sheds the least important traffic first, using criticality levels. source

4Tell the caller to slow down

What you see

Rejecting says no to one request. Backpressure goes further and tells callers to send less. Here, callers cut their send rate by 30% after any second with a rejection and add 10 requests per second back after a clean second. The dashed line is what they wanted to send.

What it tells you

With the default spike, slowing down cuts rejections from about 45 per second to about 3 and lifts useful work from about 75 to 79 per second. Callers stop sending requests that were going to be refused anyway.

The signal can travel several ways. A 429 response can carry a Retry-After header saying how long to wait. source A full bounded buffer can make a fast producer wait. In Reactive Streams, the receiver announces how many more items it wants and the sender may not exceed that, so the queues between components stay bounded. source Google's clients throttle themselves: each tracks its recent requests and accepts and, once requests pass twice the accepts, rejects new ones locally with a rising probability. source The rule in this simulation is a simpler stand-in for that.

The price

Held-back work has to go somewhere: the caller queues it, the user waits, or it is dropped. For sources that cannot be slowed, such as clock ticks or mouse movements, the Reactive Streams README says the publisher must buffer or drop. source

5Retries make overload worse

What you see

A caller whose request fails or times out tries again, up to three attempts in total. Plain retries come one second after a failure. Careful retries wait 1, 2, 4 seconds with random jitter, and only while retries stay under 10% of requests. Choose how callers retry.

What it tells you

Retries add load exactly when the server can least afford it. With plain retries and no queue limit, arrivals reach 360 per second, three times the spike, because abandoned requests come back. Useful work stays near zero long after the spike ends.

The layered version is worse. AWS gives an example of a call passing through five layers with three retries at each, where the load on the database rises 243 times, which is 3 to the fifth power. source The usual limits:

  • Retry in one place. Google lets only the layer directly above the rejecting one retry. source
  • Budget the retries. Three attempts per request limits the worst case to just under 3 times the load. A per-client rule of retries under 10% of requests keeps it near 1.1 times. source
  • Back off with jitter, so failed callers do not all come back at the same instant. source
  • Retry only what is safe to repeat. AWS notes that calls with side effects are not safe to retry unless they are idempotent. source

Switch to careful retries without a queue limit: the extra load shrinks, but the queue still fills and useful work still collapses. Then tick "bounded queue". The two work together, and useful work stays near capacity.

The price

Fewer retries means some callers give up and see an error instead of eventually succeeding.

6Every layer has its own queue

What you see

A request passes through several waiting lines before it finishes. Each one has the same three questions: what fills it, how it says no, and what to watch.

  • Accept queue: connections wait for a free worker. See how web servers run many requests at once.
  • Worker pool queue: requests wait because every worker is busy.
  • Connection pool: requests wait for one of the limited database connections.
  • Message queue: consumers fall behind producers, and the gap is the consumer lag. See the queue screen in Scaling the Backend.
  • Another service: its own queues, and its 429 or 503 comes back to you.

What to watch

Watch how long the oldest item has waited, not just how many arrive. AWS points out that queues hide age: a server can have no idea how long a request sat in line. source Compare goodput with total throughput, and watch the rate of rejections. Say no as early as possible, and make the no cheap.

The simulation has one class of caller, a fixed 100 ms service time, a fixed 5-second patience, and a rejection that costs a tenth of a request. Those figures, the 70% and +10 slow-down rule, the 1-2-4 second backoff and the arithmetic on screen 1 are examples of mine, not from the sources.
